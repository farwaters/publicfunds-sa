## Problem
The CHG-2026-033 review (X1) emptied 100 of the 247 fully present audit-opinion cells for 2022/23 in a scratch run: all tests passed. (The live file has 292 entities, 257 of them applicable to opinions, and 247 `P` cells for opinion 2022/23; an earlier note said "100 of 257", which is the applicable count, not the `P` count.) The pins in CHG-2026-033 are tests, and tests do not run in the nightly build, so a data hole that appears at night is published. Nothing compares tonight's candidate with what is already live.

## Design choices (stated plainly)
1. **Compare with the previously published file.** The candidate `coverage` document (built from the warehouse at export time) is compared with the `coverage.json` that is in `public-data/v1/` **before** the export overwrites it. No warehouse history and no extra stored state are used.
2. **BLOCK (publish refused, nonzero exit) only when** a data type and financial year whose previous count of fully present (`P`) municipalities was **at least `BLOCK_MIN_PREVIOUS` (= 5)** has **none** in the candidate. `p` (partial), `m`, `-` and `?` do not count. A data type or year missing from the candidate counts as zero.
3. **Below `BLOCK_MIN_PREVIOUS` it is a WARN.** A fall to none from 1 to 4 fully present municipalities warns (`warn: procurement 2022: 3 -> 0 (fewer than 5 before, so not blocked)`) and does not block. Reason: procurement 2019/20 has **1** and procurement 2021/22 has **3** fully present municipalities, and a procurement `P` needs at least 90 % of the matched awards to carry a value (`thusa/models/marts/100_coverage.sql`). One unvalued award or one alias re-match could therefore flip a lone `P` and block the nightly on correct data. 5 is above both and below every other guarded pair (the next smallest is 11, procurement 2022/23). A drop from 1 to 4 fully present municipalities to 0 **warns, publishes the zero, and that lower count becomes the next baseline, so the next night is silent** (0 against a previous 0 is no change). It is a judgement, chosen by the author (PublicFunds); owner to confirm in the sign-off. Boundary tested: 4 warns, 5 blocks.
4. **WARN only (never blocks) for a count drop.** When a pair's count falls by more than `WARN_DROP_SHARE` of the previous count and the previous count is at least `WARN_MIN_PREVIOUS`, a `warn:` note is printed. Both are named constants in `thusa/evidence_guard.py`.
   - `WARN_DROP_SHARE = 0.10`. **Reasoning, and an honest limit:** no night-to-night history exists to measure on (`coverage.json` was committed once, on 19 Oct 2026, all copies are byte-identical, and every build in `changes.json` shows 75.7 %). The proxy is the spread between adjacent years of the same type in the published file, for counts of 20 or more: **0 % to 2.4 %** for budget, audited actuals and UIFW; **3.1 %** for audit opinion 2021/22 to 2022/23 (255 to 247); and **9.0 %** for audit opinion 2019/20 to 2020/21 (256 to 233, which then rises 9.4 %). 10 % sits just above the largest of these and well below X1 (40.5 %, 247 to 147). It is a starting value, to be re-set after the first 30 nightly runs. A different year is a different financial year, not a different night, so this is a proxy and not a false-positive rate.
   - `WARN_MIN_PREVIOUS = 20`: a drop of one or two municipalities in a small pair is not a signal.
5. **There is no percentage BLOCK. X1 warns; a fall such as 247 to 1 passes the block rule and only warns; the lower count becomes the next baseline.** Option A for X1 was chosen by the author (PublicFunds); owner to confirm in the sign-off. **No owner decision is recorded.** Under it: emptying 100 of 247 opinion cells for one year gives `warn: audit_opinion 2023: 247 -> 147 (40.5% fewer)` and does not block; only a whole data type and year going from at least `BLOCK_MIN_PREVIOUS` fully present municipalities to none blocks. Consequences, stated so nobody is surprised: (a) 247 to 1 publishes with a warning, (b) the next night compares with 1, so a further fall from 1 to 0 is only a warning (below `BLOCK_MIN_PREVIOUS`), and (c) a slow decline that never empties a pair is never blocked. Tested on the pinned file. The CSI-053 register row (description and acceptance) is reworded accordingly in this change.
6. **First run, or no previous file:** only a file that does **not exist** is a first run: the guard passes with the note `no previous published coverage.json (first run): evidence guard skipped`.
7. **Different shape of the previous file:** if the previous file has data types or years that the candidate lacks (or the reverse), or a different `schema` value, the guard adds a visible `note:` line to its result (stderr, `data/publish-data.log`, the `evidence_guard` key of `data/publish-data.json`). A pair that is missing from the candidate still counts as zero and can block; the note only makes the difference visible instead of silent.
8. **Legitimately removed data:** a documented allow list, `config/evidence-guard-allow.yaml`, shipped as `allow: []` with a comment header (pinned by a test). An entry has `data_type`, `year`, `reason` and `date` (ISO `YYYY-MM-DD`), all required. An allowed pair no longer blocks and is reported as `allowed:`. An entry whose pair has a fully present municipality again is a `warn:` ("remove it"). Adding an entry needs an RFC row and the owner's GO, and the pin test is edited with it. **Entries live in `config/`, which is committed and public: a `reason` must name a known-error, RFC or source notice and must contain no personal information** (no names of people, no IDs, no contact details).
9. **The allow file must be a mapping with an `allow` key whose value is a list.** An empty list is fine. A missing key, `allow:` with nothing after it, a bare list, an empty file or broken YAML all block (fail closed). **A misspelled key such as `allows:` therefore blocks the publish** (it does not silently switch the list off); the message names the keys found.
10. **Fail closed, on everything.** Only a missing previous file is a first run. A previous file that exists but is unreadable, is not valid JSON, or parses to something that is not a JSON object (`null`, `[]`, `0`, `"text"`, `true`), or is a malformed coverage document (for example a cell string whose length differs from the number of years), blocks. So does a missing or malformed allow file, a YAML syntax error (`yaml.YAMLError`, for example `allow: [`), a malformed allow entry (missing key, unknown type, non-integer year, empty reason, bad or impossible date, duplicate), and **any other exception raised inside the guard**: all become `UnsafeExport("evidence guard could not run (nothing was written): <ExceptionName>: <message>")`. There is no traceback, `pf publish-data` exits 3, and nothing is written (tested, including the CLI exit code and a byte-identical output folder).
11. **Where it runs.** At the top of `publish_data.export`, right after the candidate documents are built and **before any file is written**. A block is an `UnsafeExport`, exactly like the existing quality gate: `pf publish-data` exits **3**, `scripts/publish-public-data.sh` exits 3 and commits nothing, and **the data already published stays live and untouched**. It is not a dq check: a dq failure would change the manifest's dq counts and would need the warehouse to know the published file. No connector is changed; no figure is changed.

## How an owner can override
- **The documented way:** merge an allow-list entry (RFC row + owner GO). It takes effect at the next nightly after the merge, so a false-positive block costs at least one night of staleness. This is slow on purpose: it leaves a reason and a date in git.
- **Manual run only:** for a run started by hand on a checkout, the person running it can add the entry locally without committing, or remove `public-data/v1/coverage.json` (the guard then takes the "first run" path and passes with a note). **These do not work for the nightly routine:** both dirty a tracked file, and step 0 of the nightly (CHG-2026-025: fast-forward to origin/main, stop on a dirty tracked file) stops the routine before it runs. So for the nightly the only working override is a committed allow entry that is on `main` (commit + RFC row + owner GO), effective at the next nightly. A manual bypass must be recorded in the run notes and followed by the proper commit.
- **Not included:** a one-shot command-line flag (for example `--skip-evidence-guard`). It would be a quiet way to defeat the guard and was not asked for. Listed as an open question.

## What is NOT included
- No change to any figure, connector, parser, source, raw file or to `public-data/` (not edited by hand; the first nightly after a merge writes the same files).
- No edit of the refresh skill, the refresh routine or the publish script. **WARN visibility:** warnings appear only on stderr, in `data/publish-data.log`, and in the `evidence_guard` key of `data/publish-data.json`; they are **not** in the nightly report. A block shows as exit 3. **Open item: CSI-054** (owner PublicFunds, the author; status Open; needs its own RFC and owner GO): surface guard warnings and exit 3 in the nightly report and skill.
- No check of values or amounts, of `p` (partial) cells, of the headline percentage, or of a slow decline (see design choice 5).

## Risk
- **False-positive block of the nightly (the main risk).** A legitimate removal of a whole data type and year, or a source outage that empties a pair, blocks the publish. Mitigations: the block leaves the existing live data exactly as it is (tested: byte-identical output folder); the message names the pair and the counts; the allow list is the documented way out (slow, see "How an owner can override"). Exposure today: on the pinned file, 28 pairs have at least one `P`; **26 are guarded by the block rule** and 2 (procurement 2019/20 with 1, 2021/22 with 3) only warn.
- **Fail closed** also means a corrupt `public-data/v1/coverage.json` or a bad allow file blocks the nightly until fixed (restore the file with `git checkout public-data/v1/coverage.json`).
- **What "previous" is.** The guard compares with the nightly's local `public-data/v1/coverage.json`. Nightly step 0 fast-forwards the checkout to origin/main and stops on a dirty tree, so this equals `main` unless an unpushed local data commit exists. **Not verified:** what the nightly routine does when the publish script exits 3. `itil/knowledge/runbooks.md` (RB-11) says exit 3 is "export refused: read `data/publish-data.json` / `.log`", and the skill is reported to cover only exit 4; the routine and skill were not read or changed for this RFC.
- **The WARN threshold is a guess backed by a proxy**, not by history (design choice 4). Too low gives noise that is ignored, too high misses a real drop.
- **Warn-only drops and the baseline** (design choice 5): a large partial loss publishes and becomes the baseline.
- **A block or warning is only seen if somebody looks** (see WARN visibility above).
- **Published output:** none. The return dict of `export` gains the key `evidence_guard`; no published file reads it. The manifest's dq counts are unchanged because the guard is not a dq check.
- **POPIA:** the guard reads and prints aggregate counts of municipalities per data type and year, data type names and years. No names, amounts, identifiers or suppliers are read or written. Allow-entry reasons are free text in a committed file: see design choice 8.
