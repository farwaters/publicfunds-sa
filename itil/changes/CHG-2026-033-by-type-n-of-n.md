## Problem
On `#/unknowns` the table "Share of municipality-years fully published, per province and data type" shows 83.3% in the column "Irregular & wasteful spending" for all nine provinces. A column of identical 83.3% reads as "83% of spending is irregular". It is not: it is a count of how much data is available.
Measured on origin/main 6abd695 (the committed `public-data/v1/coverage.json` and `municipalities.json` are what the page reads):

- The cell is a coverage measure (is the data there?), not an amount or a rate of irregular spending. The label (`DT.uifw`, index.html line 114) hides that; the other four labels and the CSV headers share the ambiguity.
- It is computed per municipality, not copied down from a province or national value. 83.3% = 5 of 6 financial years (2019/20 to 2024/25, FYE 2020 to 2025): all 257 existing municipalities have the UIFW data for FYE 2020 to 2024 and none for FYE 2025.
- The same pattern is in two more columns. **Audit opinion**: no municipality has 2024/25 (ceiling 83.3%; EC and GT sit at it). **Budget**: 256 of 257 municipalities have the original budget but not the adjusted budget for 2024/25, 1 has no budget data (ceiling 83.3%; LP and WC sit at it). Audited actuals have values for 246 of 257 in 2024/25 and have no such limit.
- Tender awards are low for a different reason (Change item 6).
- Nothing on the page shows n or N, the window, or which year is empty, and nothing in the tests notices any of it.
- What the data can say about the cause: the source APIs read on 2026-10-24 (live GET) end at FYE 2024 for UIFW (`uifwexp`) and audit opinions (`audit_opinions`), and `incexp_v2` has the adjusted budget (ADJB) for FYE 2023 and 2024 and 2026, **not for FYE 2025**. KE-006 records the same and marks the cause "[unverified why]". This record does not state a cause on the page, and does not say the data was or was not published by anyone. AGSA 2024-25 Annexures 1 and 3 exist as PDFs (checked 2026-10-24), so "published but not yet loaded" is right for them; the sentence is not put on the page because it is not checkable from the data (Change item 4, owner option).

2. **n/N visible, not hover.** `table()` gets opt-in hooks that every other table leaves off: a column may set `dt` (written as `data-dt` on its `th` and `td`), `marks` (small `span.ymark` lines inside the `th`) and `wrap` (header text may wrap; the number columns stay on one line), and the caller may pass `rowAttrs` (here `data-prov` on each row). For an empty-year type the cell also shows "(highest possible 83,3%)". Percentages on this page use a decimal comma (`num()` is en-ZA), so the model strings use one too (see departures).
3. **Empty-year rule, computed from `coverage.json` and descriptive only.** A window year is *empty* for a data type when no municipality has state `P` for it in that year (cells "-" and "?" ignored). ## Risk
Page wording and layout, CSV headers; no data value changes, no flags, no suppliers or people named. Risks: (1) n/N or note text diverges from the percentage: all come from the same counters; page code is run in node against the Python model on real and mutated data; `dashboard_check` asserts each cell on the page. (2) The rule misfires: tested on real data, the reviewers' mutation, partial arrival, arrival, synthetic data. (3) Wider table on narrow screens: sub-lines are inside the cells; `dashboard_check` runs both viewports. Accessibility and contrast of the new text, banner and markers: verified with axe on both viewports and both colour schemes (Test plan); the one dark-scheme finding is in the existing navigation and is also on main. (4) CSV header rename. (5) **A red tripwire without a code change (pytest gap, owner decision):** the pin tests read the committed `coverage.json`, which the nightly refresh (03:00 SAST, standing approved change) rewrites. When FYE 2025 UIFW, opinions or ADJB land in the data, or on 2026-12-01 when the window moves (Not changed), the next nightly commit turns pytest red with no code change; `scripts/bootstrap.sh` runs pytest and dies on a failure (`PF_SKIP_TESTS=1` skips), so a fresh install or a repair would fail on a data change. pytest does not test the page. Whether the pin should be a hard failure or a loud warning/`xfail` that reports without blocking bootstrap is the owner's decision (options and date under Not changed); this draft ships it as a hard failure because an unnoticed change of what the page says is the risk it exists for.
